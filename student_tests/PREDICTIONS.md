# 运行前推演

以下预期由 Codex 在补全函数和运行仿真前整理，供学生阅读与复核，不代表学生已经独立完成手算。

## 两用户基准

2 用户、2 tick，每 tick 128 bit、1 ms；用户 1 在 tick 0 到达 96 bit。
电路 tick 0 空闲，tick 1 发出 96 bit，于 2 ms 完成；分组 tick 0 发出 96+32=128 bit，于 1 ms 完成。
两者 payload 利用率 96/256=37.5%；wire 利用率分别为 37.5%、50%；无丢弃、无积压。

## 自拟边界

1. 用户 0 在 tick 0 到达 200 bit，用户 1 在 tick 1 到达 40 bit；缓存 220 bit，窗口 2 tick。
   未完成首记录仍预留全部 200 bit，因此后一条整条丢弃。
   电路只在 tick 0 发 128 bit，窗口结束积压 200 bit；分组发 128+104=232 bit，tick 1 结束交付 200 bit。
2. 用户 0 在 tick 0 到达 225 bit，包头 32 bit，窗口 2 tick。
   分组 wire=257 bit，只能发送 256 bit，完整交付为 0，原始 payload 积压 225 bit，时延无样本。
3. 仅改变 tick_ms 时，发送量、丢弃和积压不变，完成时延应按相同比例缩放。

## 四场景预测

- continuous：电路可满载交付；分组受包头开销限制，payload 利用率下降，可能丢弃和积压。
- staggered_burst：热点用户无法借用电路空闲时隙；共享 FIFO 预期交付更多、等待更短。
- synchronized_burst：两者出现排队；分组需要额外发送包头；最后一批可能留在窗口内未完成。
- light_random：总体轻载；分组通常减少等待，wire 利用率受包头影响高于 payload 利用率。

## 附加实验预测

只改变包头为 0、16、32、64、128 bit，保持相同到达、缓存、容量和窗口。
电路不使用包头，其全部结果应不变。continuous 下共享 FIFO 的 payload 交付能力预期随包头增加而下降。
只改变缓存为 512、1024、4096、8192 bit：较大缓存可能减少尾丢弃，但会留下更多积压或增加完成记录的等待，不能仅凭丢失率判定更优。
